## Результат и материалы

Подготовлен контейнер `url-probe`, который раз в минуту запускает переданный Python-скрипт `probe.py` по расписанию cron. Планировщик и скрипт работают от отдельного пользователя `appuser` с UID/GID `1001`; строки `OK`/`FAIL` каждого запуска доступны через `docker compose logs`. ## 2. Dockerfile и обоснование решения

Итоговое содержимое [Dockerfile](url-probe/Dockerfile):

```dockerfile
FROM alpine:3.18 AS supercronic-download

ARG SUPERCRONIC_VERSION=v0.2.51
ARG SUPERCRONIC_SHA1SUM=1692066e350a88ff4d7d6474fe3c7a6c41ec5e89

RUN apk add --no-cache curl \
    && curl -fsSL \
        "https://github.com/aptible/supercronic/releases/download/${SUPERCRONIC_VERSION}/supercronic-linux-amd64" \
        -o /usr/local/bin/supercronic \
    && echo "${SUPERCRONIC_SHA1SUM}  /usr/local/bin/supercronic" \
        | sha1sum -c - \
    && chmod +x /usr/local/bin/supercronic


FROM python:3.11.6-alpine3.18

SHELL ["/bin/sh", "-eu", "-c"]

ARG APP_USER=appuser
ARG APP_UID=1001
ARG APP_GID=1001
ARG APP_HOME=/app

RUN addgroup -S -g "${APP_GID}" "${APP_USER}" \
    && adduser -S -D -H \
        -u "${APP_UID}" \
        -G "${APP_USER}" \
        "${APP_USER}" \
    && mkdir -p "${APP_HOME}" /config \
    && chown -R "${APP_USER}:${APP_USER}" "${APP_HOME}" /config

COPY --from=supercronic-download \
    /usr/local/bin/supercronic \
    /usr/local/bin/supercronic

WORKDIR ${APP_HOME}

COPY --chown=${APP_UID}:${APP_GID} probe.py ./probe.py
COPY --chown=${APP_UID}:${APP_GID} crontab ./crontab

RUN supercronic -test /app/crontab

USER ${APP_USER}

CMD ["supercronic", "-split-logs", "/app/crontab"]
```

**Обоснование.** Alpine выбран для уменьшения размера, версии Python и Supercronic зафиксированы. В отдельной стадии скачивается только бинарный файл планировщика; проверка SHA-1 в фактическом логе завершилась строкой `/usr/local/bin/supercronic: OK`. Утилита `curl` и её зависимости не переносятся в финальную стадию.

Отдельный пользователь `appuser` с UID/GID `1001` запускает и Supercronic, и дочерний `probe.py`. Команда `supercronic -test /app/crontab` проверяет расписание во время сборки. Параметр `-split-logs` направляет вывод заданий в стандартные потоки контейнера, откуда его получает `docker compose logs`. URL не копируются в образ, а `PROBE_TIMEOUT` не фиксируется в Dockerfile: оба значения поступают во время запуска.

## 4. Требование 1.1: запуск probe.py не от root

В Dockerfile процессу задан пользователь:

```dockerfile
USER ${APP_USER}
```

Фактический пользователь итогового контейнера проверен отдельным запуском:

```bash
docker run --rm \
  --entrypoint /bin/sh \
  bonus-url-probe:task1 \
  -c 'id'
```

```text
uid=1001(appuser) gid=1001(appuser) groups=1001(appuser),1001(appuser)
```

UID и GID равны `1001`, а не `0`. Поскольку стандартный `ENTRYPOINT` наследует ту же инструкцию `USER`, `probe.py` также выполняется от `appuser`, а не от root.

## 7. Задание 2. Планировщик и Compose-конфигурация

Для запуска по расписанию выбран Supercronic — cron-совместимый планировщик, предназначенный для работы главным процессом контейнера. Он сохраняет окружение контейнера для дочерних процессов и направляет их стандартные потоки в логи контейнера.

Расписание находится в [url-probe/crontab](url-probe/crontab):

```cron
* * * * * python3 /app/probe.py /config/urls.txt
```

Пять полей `* * * * *` задают запуск каждую минуту. В контейнере нет бесконечного цикла и `sleep`; `sleep 5` ниже использовался только однократно в эксперименте с restart policy.

[compose.yaml](compose.yaml):

```yaml
services:
  url-probe:
    build:
      context: ./url-probe
    image: bonus-url-probe:task2
    environment:
      PROBE_TIMEOUT: "${PROBE_TIMEOUT:-2}"
    volumes:
      - ./url-probe/urls.txt:/config/urls.txt:ro
    restart: unless-stopped
```

Compose передаёт `PROBE_TIMEOUT` из файла `.env`, подключает изменяемый `urls.txt` как read-only bind mount и задаёт политику автоматического восстановления. Первоначально в `.env` было значение `PROBE_TIMEOUT=1`; в ходе проверки оно изменено на `5`, которое осталось итоговым.

Разобранная Compose-конфигурация перед сборкой содержала:

```text
environment:
  PROBE_TIMEOUT: "1"
image: bonus-url-probe:task2
restart: unless-stopped
volumes:
  - type: bind
    source: /home/rkart/projects/bonus_hw/url-probe/urls.txt
    target: /config/urls.txt
    read_only: true
```

```text
2026-10-25T16:22:00.007900060Z ... msg=starting iteration=4 ... job.schedule="* * * * *"
2026-10-25T16:22:05.609848118Z ... msg="OK   200  0.150s https://example.org" channel=stderr
probe_success{url="https://example.org"} 1
probe_http_status_code{url="https://example.org"} 200
probe_duration_seconds{url="https://example.org"} 0.15
```

После проверки повторно получены:

```text
container_after=3287bf43e5c5985706e28e13aeb803f32b30f402ce8c2a86706b52b17ca78346
started_after=2026-10-25T16:17:57.951652414Z
OK: container ID unchanged
OK: StartedAt unchanged
```

Совпали и полный container ID, и `StartedAt`. Значит, контейнер не пересоздавался и не перезапускался, а следующий cron-запуск прочитал обновлённый файл.

## 12. Требование 2.5: автоматическое восстановление контейнера

Перед экспериментом подтверждена политика и исходный счётчик рестартов:

```text
restart=unless-stopped started=2026-10-25T16:17:57.951652414Z restarts=0
```

Первая попытка с `kill -9 1` из `docker compose exec` не завершила PID 1: после пяти секунд контейнер имел прежний `StartedAt` и `restarts=0`. Этот результат не используется как доказательство восстановления.

Затем главному процессу Supercronic отправлен `SIGTERM`:

```bash
docker compose exec url-probe \
  sh -c 'kill -TERM 1'
```

Сравнение до и после:

```text
before: status=running started=2026-10-25T16:17:57.951652414Z restarts=0
after: status=running started=2026-10-25T16:26:25.638290184Z restarts=1
```

Контейнер снова находится в `running`, `StartedAt` изменился, а `RestartCount` увеличился с `0` до `1`. После восстановления Supercronic повторно прочитал расписание:

```text
2026-10-25T16:26:25.786215069Z ... msg="read crontab: /app/crontab"
```

Это подтверждает автоматический подъём после завершения главного процесса. Политика `unless-stopped` также применяется Docker после перезапуска демона, если контейнер перед этим не был остановлен вручную; фактический перезапуск всего Docker Engine в приложенной сессии не выполнялся.
